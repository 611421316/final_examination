## 1. Project Overview

This project implements a multi-agent CrewAI / Flow system for personalized restaurant review prediction.

Given a `user_id` and an `item_id`, the system retrieves and analyzes user behavior, restaurant/business information, historical review patterns, and general restaurant rating knowledge. The final goal is to predict:

- The star rating the user may give to the business
- A realistic Yelp-style review text the user may write

The expected final output format is:

```json
{
  "stars": 4.0,
  "review": "The food was good and the service was friendly. Overall, I had a pleasant experience."
}
```

The system was tested using samples from `test_review.json`.

---

## 2. System Architecture

The system is built with CrewAI agents and Flow execution.

The main architecture contains:

| Component | Description |
|---|---|
| Flow | Controls the overall input and execution pipeline |
| Crew | Groups agents and tasks together |
| Agents | Specialized LLM workers responsible for different subtasks |
| Tasks | Step-by-step instructions assigned to agents |
| Tools | Retrieval/search functions used by agents |
| Knowledge / RAG | Retrieves relevant user, item, and review information |
| Vector Database | Stores embedded knowledge for semantic search |

---

## 2.1 Flow to Run the Crew

The evaluation pipeline uses this flow to run the Crew:

```text
run_test.py
    |
    v
WebSociety Simulator
    |
    v
CrewAISimulationAgent
    |
    v
AgentSocietyServingFlow
    |
    v
Selected Crew
    |
    v
JSON output
    |
    v
Evaluation report
```

In `run_test.py`, the WebSociety Simulator loads the test tasks and sets `CrewAISimulationAgent` as the simulation agent.

`CrewAISimulationAgent` extracts the `user_id` and `item_id`, injects the simulator interaction tool, and starts `AgentSocietyServingFlow`.

Inside `serving_flow.py`, the selected Crew is executed using this line:

```python
result = SequentialCrew().crew().kickoff(inputs=inputs)
```

This line can be changed to run another Crew mode:

```python
result = HierarchicalCrew().crew().kickoff(inputs=inputs)
```

or:

```python
result = CollaborativeCrew().crew().kickoff(inputs=inputs)
```

After the Crew finishes, the Flow extracts the predicted `stars` and generated `review`, returns them as JSON, and `run_test.py` evaluates the result and saves the final report.

## 3. Crew Members / Agents

The system uses several specialized agents.

| Agent Name | Role | Main Responsibility |
|---|---|---|
| `internet_researcher` | Restaurant Trend Researcher | Provides general restaurant rating behavior patterns |
| `user_analyst` | Yelp User Profiler | Analyzes user preferences, rating habits, and historical review behavior |
| `item_analyst` | Yelp Restaurant Analyst | Analyzes business features, strengths, weaknesses, and public sentiment |
| `prediction_modeler` | Review Prediction Expert | Predicts the final star rating and generates the review text |
| `reviewer` | Review Prediction Evaluator | Reviews draft predictions in collaborative mode |
| `project_manager` | Project Manager | Coordinates and delegates tasks in hierarchical mode |

### Agent Responsibilities

The agents are designed with strict role separation.

The `internet_researcher` only provides general knowledge about restaurant rating behavior. It does not invent facts about the specific user or business.

The `user_analyst` retrieves and analyzes information about the target user, including average rating, review count, rating tendency, common preferences, and sentiment tendency.

The `item_analyst` retrieves and analyzes information about the target restaurant or business, including categories, rating, review count, strengths, weaknesses, and public sentiment.

The `prediction_modeler` combines retrieved user evidence, item evidence, and general restaurant rating patterns to predict the final stars and generate a realistic Yelp-style review.

The `reviewer` is used in collaborative mode to evaluate whether the predicted rating and review are consistent, realistic, and grounded in retrieved evidence.

The `project_manager` is used in hierarchical mode. It coordinates the workflow and delegates tasks to the correct agents. The Project Manager should not directly perform user analysis, item analysis, or final prediction.

## 4. Collaboration Design

This project implemented and compared multiple Crew workflows:

1. Sequential mode
2. Collaborative-style mode
3. Hierarchical mode

---

## 4.1 Sequential Mode

In sequential mode, agents work one after another. Each task output becomes context for the next task.

```text
Input: user_id + item_id
        |
        v
Internet Researcher
        |
        v
User Analyst
        |
        v
Item Analyst
        |
        v
Prediction Modeler
        |
        v
Final JSON Output
```

### Strengths

- Simple workflow
- Easy to debug
- Clear task order
- Lower coordination complexity

### Weaknesses

- Agents do not revise each other's outputs
- If an early task produces weak context, the final prediction may be affected

---

## 4.2 Collaborative Mode

The collaborative workflow is a collaborative-style sequential process. Agents collaborate through task outputs, but they do not necessarily run in parallel.

```text
Input: user_id + item_id
        |
        v
Internet Researcher
        |
        v
User Analyst
        |
        v
Item Analyst
        |
        v
Collaborative Reasoning
        |
        v
Draft Prediction
        |
        v
Reviewer
        |
        v
Final Prediction
        |
        v
Final JSON Output
```

### How Agents Collaborate

The collaboration happens through intermediate outputs:

1. The `internet_researcher` provides general rating patterns.
2. The `user_analyst` analyzes the user's historical behavior.
3. The `item_analyst` analyzes the business characteristics.
4. The `prediction_modeler` compares user preferences with business features.
5. The `reviewer` evaluates the draft prediction.
6. The `prediction_modeler` produces the final JSON output.

### Strengths

- More quality control than simple sequential mode
- Reviewer can detect inconsistent predictions
- Better preference estimation in testing

### Weaknesses

- More tasks require more LLM calls
- More likely to hit rate limits
- Slower than a simple sequential pipeline

---

## 4.3 Hierarchical Mode

In hierarchical mode, a Project Manager coordinates the workflow and delegates tasks to specialized agents.

```text
Input: user_id + item_id
        |
        v
Project Manager
        |
        | delegates tasks
        v
+------------------------------+
| Restaurant Trend Researcher  |
| Yelp User Profiler           |
| Yelp Restaurant Analyst      |
+------------------------------+
        |
        v
Review Prediction Expert
        |
        v
Final JSON Output
```

### How Agents Collaborate

The `project_manager` is responsible for workflow coordination. It delegates:

1. General restaurant rating pattern analysis to the `internet_researcher`
2. User analysis to the `user_analyst`
3. Business analysis to the `item_analyst`
4. Final prediction to the `prediction_modeler`

The Project Manager should not directly analyze user data, item data, or generate the final answer.

### Strengths

- Clear coordination through manager agent
- Better review generation performance in testing
- Highest overall quality score in the experiment

### Weaknesses

- More coordination overhead
- Longer runtime than collaborative mode
- Manager configuration must be strict

## 7.3 Problem Encountered: Rate Limit

The main problem encountered during testing was rate limiting from the LLM provider.

Because the Crew contains multiple agents, one prediction may require many LLM requests. When testing many samples from `test_review.json`, the system sometimes sent too many requests in a short time.

In the collaborative report, some generated outputs contained rate limit messages such as:

```text
litellm.RateLimitError: RateLimitError: OpenAIException - Error code: 429 - {'status': 429, 'title': 'Too Many Requests'}
```

This shows that even when the final report counted `errors = 0`, rate limit problems could still appear inside individual task outputs.

---

## 7.4 Solution: Add `max_rpm=5`

To reduce rate limit errors, I added `max_rpm=5` to the Crew configuration.

Example:

```python
crew = Crew(
    agents=agents,
    tasks=tasks,
    process=Process.hierarchical,
    verbose=True,
    max_rpm=5
)
```

The `max_rpm=5` setting limits the number of requests per minute. This makes the system more stable and helps avoid provider rate limit errors.

### Trade-off

The main trade-off is runtime. After adding request throttling, the system becomes more stable, but each experiment takes longer to finish.

## 8.4 Analysis of Results

The sequential mode had the lowest performance in this experiment. It achieved an overall quality score of `0.6567` and produced `2` timeout errors. It was also the slowest mode, requiring `9133.89` seconds, or about `152.23` minutes.

The collaborative mode was the fastest. It completed inference in `6386.34` seconds, or about `106.44` minutes. It also achieved the best preference estimation score:

| Mode | Preference Estimation |
|---|---:|
| Sequential | 0.6623 |
| Collaborative | **0.7617** |
| Hierarchical | 0.7400 |

This means collaborative mode was the best at estimating user preference.

However, hierarchical mode achieved the best review generation quality:

| Mode | Review Generation |
|---|---:|
| Sequential | 0.6511 |
| Collaborative | 0.6992 |
| Hierarchical | **0.7314** |

As a result, hierarchical mode achieved the best overall quality:

| Mode | Overall Quality |
|---|---:|
| Sequential | 0.6567 |
| Collaborative | 0.7305 |
| Hierarchical | **0.7357** |

Although hierarchical mode was slower than collaborative mode, it produced the strongest review generation score and the highest overall quality.

---

## 8.5 Final Performance Conclusion

The hierarchical Crew achieved the best overall quality score, while the collaborative Crew was faster and achieved the best preference estimation.

Sequential mode was the simplest workflow, but it performed the worst in this experiment. It also had two timeout errors and the longest runtime.

For the final system, hierarchical mode is selected because it produced:

- The highest overall quality score
- The best review generation performance
- Stable execution with 0 reported errors

Collaborative mode remains useful because it was faster and produced the best preference estimation score.
